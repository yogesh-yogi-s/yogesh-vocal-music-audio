# Architecture

VMA has three deliberately separate concerns: container storage, application inspection/extraction, and optional browser playback. The format library never needs a media decoder to store or extract a stream.

## Application flow

The browser uploads two source files to FastAPI. Each request is written to a UUID-named directory below process-owned temporary storage, then routed through `backend.app.vma_service` and the independent `backend.vma` library. With no requested version, two valid PCM WAV uploads create V1; other accepted inputs create V2 and store the supplied files as opaque source bytes. If both upload names use `.wav` but either payload is not valid RIFF/WAVE data, the backend rejects the pair with HTTP 422 rather than falling back to V2. A forced V1 request rejects inputs that do not satisfy the V1 PCM WAV rules.

Each uploaded file is limited to 500 MiB by default by the application adapter; `VMA_MAX_UPLOAD_BYTES` can lower this ceiling for constrained previews. A parser-reported size is rejected before an application destination is created, and the streamed copy independently counts bytes so enforcement does not depend on caller metadata. Partial application copies and failed session directories are removed. Client filenames never select storage paths: generated application names are used on disk, and only a bounded, control-character-free basename is retained as V2 metadata. Caller media types are accepted only when they use a valid bounded type/subtype token form; recognized audio labels still depend on file identity rules rather than caller claims. A public deployment must additionally configure an equivalent request-body limit at its ingress so oversized multipart bodies are rejected before framework spooling.

An outer ASGI resource middleware checks `Content-Length` before multipart parsing and also counts streamed bodies when no trustworthy length is available. Two-file creation allows twice the configured per-file limit plus 2 MiB of multipart overhead; single-upload routes allow the configured per-file limit plus 2 MiB. Per-file streaming validation remains authoritative. Application-owned sessions and request work live below one process temp root, with admission reservations for worst-case input/output duplication. The default process budget is 8 GiB, with three expensive requests active at once. Admission rejects new work with 507 rather than deleting existing sessions. Framework multipart spools also use the operating-system temp location, so a public runtime must bound that filesystem independently.

The welcome demo is a fixed, application-owned V1 asset. `POST /api/demo` accepts no file or path and copies only that asset into a newly allocated ordinary UUID session. The resulting payload enters the same inspection and browser playback pipeline as user-owned files. Demo sessions are not shared globals, the bundled asset is never written, and a failed demo request removes only its newly allocated session directory.

Opened containers receive an opaque session UUID, but that identifier is never an authorization credential. The browser also receives a cryptographically random ownership token in an `HttpOnly`, `SameSite=Strict`, `/api` cookie; it is `Secure` everywhere except genuine loopback HTTP development. Each session stores only the token's SHA-256 digest. Every session inspect, stream, extraction, download, and deletion route compares that digest before accessing the directory and returns the same generic 404 for a missing, expired, deleted, or foreign session. Browser state-changing routes validate same-origin requests and Fetch Metadata when available; no credentialed CORS policy is enabled.

One browser token may own multiple separate session directories. This supports refreshes and tabs without replacing or invalidating another active personal or demo session. `DELETE /api/vma/{session_id}` first tombstones the owned session so new work is rejected, then removes it immediately or after an in-flight file response releases its lease. Session directories expire after two hours of inactivity, are periodically cleaned, and are removed when the application stops. There is no database, account system, cloud storage, or durable session state. The in-process lease table and process-local temporary directory assume one application process; a multi-worker deployment requires a shared ownership/session store with distributed expiry/deletion coordination or verified sticky routing.

At most two operations lease one session concurrently, which permits the normal two-stem playback fetch while bounding extraction amplification. Every stream or extraction request writes into a unique response directory, so concurrent requests cannot overwrite one another. Failure paths remove partial response directories; successful response directories are removed after streaming. Periodic expiry scans run in a worker thread and skip active leases. Async routes offload parsing, container construction, extraction, and ZIP work through a bounded request admission layer, and cancellation waits for an already-started worker before cleanup so files are not removed underneath an active writer.

An outer deployment-security middleware validates the Host header before routing and strips all forwarding metadata from untrusted peers. Only peers within `VMA_TRUSTED_PROXIES` may supply forwarded scheme, host, or client addresses; the client address is selected by walking the chain from the nearest configured proxy toward the first untrusted address. Uvicorn proxy processing is disabled so it cannot rewrite the ASGI peer before this check. Every startup requires an explicit environment mode; production startup fails unless trusted hosts, HTTPS browser origins, and an exact trusted health-check hostname are configured. The outer middleware rejects hostile browser origins for every multipart workflow before FastAPI parses the body, while endpoint checks remain as defense in depth. Production disables the CDN-backed interactive documentation routes rather than weakening the application CSP. Rate accounting therefore uses either the direct connection peer or the client resolved through that explicit proxy boundary. Defaults use a 60-second window with category limits documented in the README.

The same outer middleware rejects cross-site Fetch Metadata and unapproved supplied origins on every expensive stateless multipart route before request admission or multipart parsing. Programmatic clients that supply neither browser header remain supported. V2 `extract-stream` requests use the extraction rate bucket and reserve the maximum browser-session container size: twice the configured per-file limit plus 2 MiB multipart overhead. This is the largest possible validated payload because the extractor copies one payload whose range must remain within that bounded session container.

The deployment middleware adds a practical same-origin CSP and common browser security headers to every response. The CSP currently permits inline script only for the pre-paint theme initializer; no third-party script, style, frame, object, or network origin is allowed. Correlation logging records a generated or syntactically safe caller request ID plus method, coarse route category, status, and duration, never the cookie, audio, query string, or full session URL. `/api/health` is a dependency-free liveness signal; `/api/ready` confirms startup completed and the configured application storage remains present and disk-accessible.

All ownership keys, limiter state, active-work counts, storage reservations, and session directories remain process-local. The only supported deployment is one application process. Multiple workers or replicas require shared state, storage, quota/rate coordination, and deletion/expiry locking. A reverse proxy must provide connection limits and slow-client/header/body timeouts; application middleware cannot solve resource exhaustion that occurs before a complete request reaches ASGI, and the application deliberately does not impose an arbitrary processing timeout on valid large operations.

## Container layers

- **V1 (`backend/vma/`)** is frozen and contains the PCM WAV parser, V1 binary reader/writer/validator (with distinct error separation for unsupported stream types, unknown codec identifiers, and unsupported codecs), WAV reconstruction extractor, and V1 frame-offset support.
- **V2 (`backend/vma/v2/`)** is frozen and stores original stream payload bytes with generic descriptors. It reads, validates, and extracts bytes directly without media inspection or decoding.
- **Version dispatch (`backend/vma/dispatch.py`)** selects the V1 or V2 reader from the shared magic and version field.
- **Format utilities (`backend/vma/formats/`)** provide the append-only FORMAT_ID registry plus limited identity/probe helpers. They do not establish decoder capability.

API routes delegate binary parsing, creation, validation, and extraction to these layers rather than packing container fields themselves. V1 `create_vma()` accepts non-negative `vocal_start_sample` and `music_start_sample` frame offsets. The current application does not offer caller-defined V2 timing overrides.

## Inspection, extraction, and playback

V1 session routes expose reconstructed WAV streams and V1 bulk extraction. V2 session routes expose per-stream downloads through `extract-stream/{stream_id}`; those downloads are the exact original payload bytes. V2 inspection and extraction do not depend on a stream being playable.

For either active version, the frontend fetches the relevant stream bytes and attempts native `AudioContext.decodeAudioData()` decoding. It uses decoded buffers only in memory; it never replaces container payloads. When both streams decode, the frontend schedules them on one `AudioContext` timeline with individual gain nodes and a master gain node. When one stream decodes, it exposes a clearly degraded single-stream player; when neither does, it keeps inspection and download controls available and hides the player. Browser support depends on the real bytes, codec, and browser implementation—not on an extension, MIME type, or FORMAT_ID alone.

Seeking is committed on the position control's `change` event, avoiding continuous source recreation while dragging. An activation token invalidates late asynchronous fetch/decode work when the active container changes; stopping/switching cleans up active source nodes and timer state.
